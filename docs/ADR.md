# Архитектурные решения (ADRs) для ReviewsAnalyzer

## ADR-1: Java + Spring Boot для Backend API

**Решение:** для разработки серверной части выбраны Java и Spring Boot.

**Причины:** развитая экосистема Spring, поддержка REST API, удобная интеграция с базами данных, брокерами сообщений и внешними сервисами, возможность разделения бизнес-логики на независимые компоненты.

**Альтернативы:** Node.js + Express, Python + FastAPI, Python + Django.

---

## ADR-2: MySQL как основная база данных

**Решение:** MySQL используется для хранения пользователей, проектов, отзывов и результатов анализа.

**Причины:** надежность, поддержка транзакций, обеспечение целостности данных, хорошая производительность и широкое распространение.

**Альтернативы:** PostgreSQL, MariaDB, MongoDB.

---

## ADR-3: Распределенная событийно-ориентированная микросервисная архитектура

**Решение:** система построена на основе распределенной микросервисной архитектуры с событийно-ориентированным взаимодействием между сервисами. Каждый микросервис отвечает за отдельную область бизнес-логики, а обмен данными и запуск операций осуществляются посредством событий и сообщений через брокер сообщений.

**Причины:** независимое масштабирование сервисов, слабая связанность компонентов, возможность асинхронной обработки операций, изоляция сбоев и упрощение дальнейшего развития системы.

**Альтернативы:** монолитная архитектура, распределенная архитектура с преимущественно синхронным взаимодействием через REST API.

---

## ADR-4: Интеграция Google Gemini через API

**Решение:** для интеллектуального анализа отзывов используется языковая модель Google Gemini, доступная через внешний API.

**Причины:** отсутствие возможностей обучать и разворачивать модель, использование готовых возможностей генеративного ИИ, снижение требований к вычислительным ресурсам и простота интеграции.

**Альтернативы:** OpenAI API, Mistral API, локальное развертывание LLM.

---

## ADR-5: OAuth 2.0 и Keycloak для аутентификации и авторизации

**Решение:** для централизованного управления аутентификацией и авторизацией используется Keycloak с применением протокола OAuth 2.0.

**Причины:** централизованное управление пользователями и клиентами, поддержка выдачи токенов доступа, разграничение прав, возможность организации безопасного взаимодействия между микросервисами и клиентскими приложениями.

**Альтернативы:** самостоятельная реализация механизма аутентификации на основе JWT и Spring Security, использование других решений для управления идентификацией и доступом.

---

## ADR-6: RabbitMQ для асинхронного взаимодействия

**Решение:** RabbitMQ используется в качестве брокера сообщений для организации асинхронного взаимодействия между микросервисами.

**Причины:** возможность передавать события и задачи без прямой зависимости сервисов друг от друга, поддержка очередей сообщений, снижение связанности компонентов и распределение нагрузки.

**Альтернативы:** Apache Kafka, Redis Pub/Sub, синхронное взаимодействие через REST API.

---

## ADR-7: Docker для контейнеризации

**Решение:** микросервисы и необходимые инфраструктурные компоненты запускаются в Docker-контейнерах.

**Причины:** единообразие окружений разработки и развертывания, изоляция зависимостей, упрощение запуска и управления компонентами системы.

**Альтернативы:** виртуальные машины, непосредственное развертывание приложений на сервере.

---

## ADR-8: Централизация записи в базу данных

**Решение:** ответственность за изменение данных в основной базе MySQL возложена на `core`. Другие компоненты взаимодействуют с данными через предусмотренные механизмы межсервисного взаимодействия.

**Причины:** централизованное управление изменением данных, сохранение целостности бизнес-логики, снижение риска конфликтов при одновременном изменении записей.

**Альтернативы:** совместная запись нескольких микросервисов в одну базу данных, отдельная база данных для каждого микросервиса.

---

## ADR-9: REST API для взаимодействия с клиентом

**Решение:** взаимодействие клиентской части с серверной осуществляется через REST API с передачей данных в формате JSON.

**Причины:** независимость клиентской и серверной частей, стандартизированный обмен данными, простота интеграции с веб-клиентами и возможность дальнейшего расширения клиентской части.

**Альтернативы:** GraphQL, SOAP, gRPC.
